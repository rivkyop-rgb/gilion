# שלב 01 — Auth, Multi-tenancy ולוג ביקורת

## מטרה

בסוף השלב משתמש מתחבר, בוחר עסק פעיל, ורואה מעטפת מערכת שהניווט בה משתנה לפי תפקידו — וכל שאילתה במערכת מוגבלת אוטומטית לעסק הפעיל.

## תלויות

0.

## מקורות באפיון

FR-1 · FR-2 · FR-8 · FR-9 · FR-10 · US-004, US-008, US-010 (מקורות ה־AuditLog) · ישויות: `Business`, `User`, `UserMembership`, `AuditLog`

## Scope

**נכנס:** Auth.js עם סשן · מסך התחברות · בחירת עסק פעיל · Prisma extension לאכיפת tenancy · מטריצת RBAC ל־5 תפקידים · `withAudit()` · מעטפת פנימית (סיידבר + סרגל עליון) עם הסתרת פריטים לפי תפקיד.

**לא נכנס:** רישום עצמי · שחזור סיסמה · הזמנת משתמשים · ניהול משתמשים ב־UI (Admin מוסיף חברויות דרך seed ב־MVP) · SSO · התחברות לקוח לפורטל (שלב 09).

## מודל נתונים

`Business` — `id`, `name`, timestamps.

`User` — `id`, `name`, `email` (unique), `user_type: [internal, customer]`, timestamps. פלוס `password_hash` שאינו ב־ERD אבל נדרש למימוש credentials-based auth.

`UserMembership` — `id`, `user_id`, `business_id`, `customer_id?`, `role: [admin, sales, designer, accounting, customer]`, `status: [active, inactive]`, timestamps.

`AuditLog` — `id`, `business_id`, `user_id`, `action` (7 ערכים), `target_type`, `target_id`, `old_value: Json?`, `new_value: Json?`, `created_at`.

**אינדקסים:**

```prisma
@@unique([user_id, business_id])           // UserMembership — חברות אחת לעסק
@@index([business_id, status])             // UserMembership
@@index([business_id, created_at(sort: Desc)])  // AuditLog — עמוד הביקורת
@@index([target_type, target_id])          // AuditLog — היסטוריה של רשומה
```

**Constraints:** `UserMembership.customer_id` חובה כאשר `role = 'customer'`, ואסור אחרת — נאכף ב־CHECK constraint ובדומיין. `Business` ו־`AuditLog` הם `onDelete: Restrict`.

| ------------------------------------------------------ | --------------------------------------------------------- |
| `GET /login`                                           | מסך התחברות                                               |

| `POST` (Server Action) `signOut`                       |                                                           |

**מודולי ליבה:**

- `lib/auth/session.ts` — הגדרת Auth.js, callbacks שמכניסים `businessId` ו־`role` ל־JWT.
- `lib/auth/tenant.ts` — `getTenantContext()`. זורק `NoActiveBusinessError` כשאין עסק פעיל, וה־middleware מתרגם לניתוב ל־`/select-business`.
- `lib/auth/rbac.ts` — `can(role, action)` + `requireRole(...roles)`.
- `lib/data/db.ts` — ה־Prisma client המורחב (`conventions.md` §2).
- `lib/data/audit.ts` — `withAudit()` (`conventions.md` §6).
- `middleware.ts` — משתמש בלי סשן → `/login`; משתמש בלי עסק פעיל → `/select-business`; `user_type = 'customer'` שמנסה להיכנס ל־`(internal)` → 403 (FR-9).

**מעטפת המערכת** לפי [`../design/app-shell.md`](../design/app-shell.md), עם שלושת התיקונים שהמסמך דורש:

## כללי ולידציה

- מייל תקין; סיסמה 8+ תווים.
- כישלון התחברות מחזיר הודעה גנרית אחת ("שם משתמש או סיסמה שגויים") — לא מגלה אם המייל קיים.

- `AuditLog` — כתיבה בלבד. אין Server Action לעדכון או מחיקה, ו־`lib/data/audit.ts` לא חושף כאלה.

## סטיות והכרעות שהתגלו במימוש

חמישה דברים שהשלב לא צפה, ותקפים מכאן והלאה:

1. **Auth.js מותקן פעמיים.** ה־middleware רץ ב־Edge runtime שלא יכול לטעון Prisma ו־bcrypt. `lib/auth/edge.ts` הוא מופע ללא providers שרק מאמת JWT קיים; `lib/auth/config.ts` הוא המופע המלא ב־Node. השניים חולקים את `lib/auth/session-shape.ts` כדי שלא ייפרדו.
2. **היעד אחרי התחברות נקבע בשרת ולא ב־`redirectTo`.** `redirectTo` של Auth.js מבצע ניווט צד־לקוח שעוקף את ה־middleware — וכך משתמש `customer` נחת על הדשבורד הפנימי, הפרה ישירה של FR-9. `destinationFor()` ב־`app/(auth)/login/actions.ts` מחליט לפי `user_type` ומספר החברויות.
3. **החלפת עסק לא יכולה לעבור דרך `form` בתוך `DropdownMenuItem`.** Radix סוגר את התפריט ומפרק את ה־form לפני שהבקשה יוצאת. הפעולה מקבלת את המזהה כארגומנט ומופעלת מ־`onSelect` עם `preventDefault` ו־transition, ואחריה `revalidatePath("/", "layout")` כי המעטפת קוראת את העסק הפעיל ב־layout.
4. **ה־scope ממוזג ל־`where` ולא נעטף ב־`AND`.** `findUnique`/`update`/`delete` דורשים שהשדה הייחודי יישאר ברמה העליונה; עטיפה ב־`AND` הייתה שוברת אותם.
5. **Playwright רץ סדרתית.** שרת הפיתוח מהדר מסלולים לפי דרישה, ושלושה workers הופכים כל ניווט ראשון ל־timeout. `workers: 1` ו־`timeout: 60s`. CI מול בילד חם יוכל להעלות.

**מלכודת בדיקה ששווה לזכור:** `fetch("/api/auth/session")` נענה ממטמון הדפדפן, ולכן החלפת עסק נראתה כאילו לא קרתה בזמן שהממשק כבר התחלף. הבדיקות אומתות מול מה שהמשתמש רואה, וה־endpoint הוא בדיקה משנית עם cache-busting.

## תוספת: הרשאות ניתנות לעריכה לכל עסק (29/08/2026)

מטריצת ההרשאות ב־`lib/auth/rbac.ts` נשארת **ברירת המחדל**, ועסק יכול להזיז תא. הטבלה `RolePermission` שומרת **רק את ההבדלים**, כך שתא שלא נגעו בו ממשיך לעקוב אחרי ברירת המחדל — גם כשזו תשתנה בעתיד. שמירת המטריצה כולה הייתה מקפיאה את ברירות המחדל של היום לתוך כל עסק שאי פעם פתח את המסך.

**זה אינו סותר את האפיון.** `prd.md` §181 מוציא מה־MVP *"הרשאות מותאמות אישית **מלאות**, **יצירת** תפקידים ו**שכפול** תפקידים"* — כלומר תפקידים חדשים. חמשת התפקידים נשארים קבועים. ו־FR-8 עצמו מנסח את היעדר גישת הגרפיקאית לתשלומים כ**ברירת מחדל**.

### שלושה תאים נעולים, מסיבות שונות

1. **`admin` × `settings` חייב להישאר `write`.** זה המסך שעורכים עליו הרשאות, ולכן הורדתו מוחקת את הדרך היחידה להעלות אותו בחזרה. אין חזרה דרך הממשק — רק מנהל־על או המסד.
2. **תפקיד `customer` אינו ניתן לעריכה כלל.** FR-9 מגדיר את גבול הפורטל, והוא אינו של עסק בודד להזיז.
3. **`portal` ו־`platform` אינם ניתנים לעריכה לאף תפקיד.** הראשון ללקוחות בלבד; השני אינו נגזר מהחזקת תפקיד, ולכן תא במטריצה עבורו חסר משמעות.

**התאמה על תא נעול מתעלמים ממנה ולא מצייתים לה** — שורה שלא הייתה אמורה להיכתב לא תהפוך לאפקטיבית רק משום שהיא קיימת.

### החתימה שונתה כדי ש־TypeScript יאכוף

`requireAccess(role, area)` הוחלף ב־`requireArea(ctx, area)` שמקבל את ההקשר כולו, וכך נדרש עדכון של **כל 40 נקודות האכיפה**. חתימה שממשיכה לקבל תפקיד בלבד הייתה מאפשרת למסך לשכוח את ההתאמות ולהמשיך לאכוף ברירות מחדל בשקט — כשל שקט הוא בדיוק מה שאסור באכיפת הרשאות.
